# 验收标准（Acceptance Criteria）：严格但不复杂
> 阶段标签：P · C（旧标签，以头部 PDCA 标签为准）

> 版本：v1.1.0 | 更新：2026-07-13
> 用途：定义"做完了"的硬标准——DoD（完成的定义）+ 验收标准（AC，Given/When/Then 格式）+ 4 道质量闸门。结合本框架已有的「对抗性审查」(找茬执行) 与「Red Flags」(偏离报警) 作为验收的执行层。纯文本、零外部依赖，内网可用。

### 📖 什么时候读这个文件

- 任务要"定验收标准 / 定 DoD / 写验收条件 / 怎么算做完了"时
- 你说"验收标准严格点 / 定个验收 / 给个 DoD / acceptance criteria"
- 写 spec 的「验收标准」小节时（先读这个，再写）
- 验收阶段（§6 Check）逐条对照核对时

🔴 **不要在这时候读**：纯问答 / 查个东西且无验收需求时。

**主动扫描时机**：接到"验收严格点"类需求时；写 spec 准备填验收标准时；验收阶段准备逐条核对前。

## 一、先搞清楚：DoD 和 验收标准 是两回事（大白话）

用盖楼打比方，一下就懂：

- **DoD（Definition of Done，完成的定义）** = "一栋楼封顶算不算交工？" 不算。得**通水通电、消防验收合格、能住人**——这是**所有楼**都要过的**通用底线**。不管盖什么楼，这条底线不能少。
- **验收标准（Acceptance Criteria，AC）** = "这栋楼是你定制的：主卧要朝南、厨房要 8 平米、电梯到户"——这是**这一栋楼**专门的要求。过了才说明"盖对了**你**的楼"。

| 维度 | DoD（通用底线） | 验收标准 AC（你的专属要求） |
|------|----------------|---------------------------|
| 回答的问题 | "做得规不规矩？" | "做没做对你想要的？" |
| 适用范围 | 所有任务都过同一套 | 每个任务单独写 |
| 谁定 | 框架默认给（见第三节闸门1） | 你和 AI 在 spec 里一起定 |
| 不过会怎样 | 不能算"做完"，一律打回 | 这条功能算没做对，要改 |
| 类比 | 交房通用验收（水电消防） | 你买房时的定制清单 |

> **核心逻辑**：DoD 管"规不规矩"，AC 管"对不对你的需求"。**两者都过，才叫真做完**。只过 DoD 没过 AC = 楼盖得合规但不是你要的那栋；只过 AC 没过 DoD = 你要的户型有了但水电没通，住不了。

## 二、验收标准怎么写（Given/When/Then，0 基础也会写）

验收标准最怕写成"做好就行""性能好"——这种话**没法验收**，AI 会自己定标准，一定往最省事的方向偏。

用固定三句式写，像"考试卷的答案"一条条对着查：

| 部分 | 中文 | 作用 | 写法示例 |
|------|------|------|----------|
| **Given（给定）** | 在什么前提 / 状态下 | 锁死前置条件，避免"环境不同结果不同" | 给定用户已登录、余额为 100 元 |
| **When（当）** | 做了什么操作 | 说清动作，不模糊 | 当用户点击"提现 30 元" |
| **Then（那么）** | 应该出现什么结果 | 写**能测量**的结果，不写感受 | 那么余额变为 70 元，且到账记录 +1 条 |

**完整示例（常见场景）**：
```
AC-1: 给定用户已登录且余额为 100 元，
      当用户点击"提现 30 元"，
      那么余额变为 70 元，且生成 1 条到账记录。

AC-2: 给定用户已登录且余额为 20 元，
      当用户点击"提现 30 元"，
      那么提示"余额不足"，余额保持 20 元不变。
```

**为什么非用这个格式不可**：
> AI（和人）都会"照字面优化"——**你只验收你写明的，没写明的就等于没要求**。验收标准写得像考试答案，AI 才不敢偷工；写成"做好就行"，AI 一定按最省力版本交差。

**三条硬性写法规则**：
1. **能测量**：写"响应 < 500ms""余额变 70 元"，不写"速度快""没问题"。
2. **有边界**：正常情况写一条，异常情况（余额不足 / 空输入 / 网络断了）也要写一条（见 AC-2）。
3. **对得上需求**：每条 AC 都能回溯到 spec 里的一个需求点，别写 spec 没提的东西。

## 三、4 道质量闸门（把"严格"落进流程）

结合本框架现有流程（Plan → Do → Check），把"严格验收"拆成 **4 道闸门**。每道不过，不许进下一道——这就是"严格"的具体落地，不是喊口号。

```
任务流：Plan（想清楚）→ Do（做）→ Check（验收）
                              │
        ┌─────────────────────┴─────────────────────┐
        │          4 道质量闸门（逐道过）              │
        │                                              │
        │  闸门1 动手前：规格自检（写清 5 块）          │
        │       ↓ 不过 = 不许动手                      │
        │  闸门2 改完后：只看差别（没偷偷改别的）        │
        │       ↓ 不过 = 打回                          │
        │  闸门3 有测试：测试真能抓错（变异思想）        │
        │       ↓ 不过 = 测试无效，重做                │
        │  闸门4 你拍板：人工签收（看过具体行）          │
        │       ↓ 不过 = 不算做完                      │
        └────────────────────────────────────────────┘
```

### 闸门1：动手前——规格自检（Pre-prompt spec check）

**做什么**：写 spec 时，必须把下面 5 块写清楚，少一块不许进 Do 阶段。
1. **问题**：要解决什么？（一句话）
2. **范围**：这次做哪些？（列清单）
3. **不做的事（Non-goals）**：这次**明确不做**哪些？（防止 AI 画蛇添足）
4. **验收标准**：按第二节 Given/When/Then 写，每条能测量
5. **风险**：可能出什么岔子？怎么兜？

**对应本框架**：§6 /plan 步骤4（P.design）（第一性原理拆解）+ `references/common/pda/document_specs.md`（No Placeholders + Self-Review）。

> 类比：动手术前先写"手术同意书+方案"——没写清切哪、不切哪、出事怎么办，医生不能下刀。

### 闸门2：改完后——只看差别（Post-gen diff review）

**做什么**：验收时只核对一件事——"AI 说的和做的一致不一致"：
- ✅ 声明要改的文件，真的改了
- ✅ 没偷偷改别的文件（没越权）
- ✅ 没私自加依赖 / 装包（没引入新风险）

**对应本框架**：§2 文件变动声明「五要素」（路径/类型/位置/内容/目录结构）+ 铁律6「回溯保障」（动手前先 commit，改错能回退）。

> 类比：装修工说"我只动了客厅"，你验收就查——客厅改了没？卧室厨房是不是也被动了？有没有偷偷加项目。

### 闸门3：有测试就——测试要真能抓错（Test evidence + mutation）

**做什么**：测试不是"跑了就过"。要证明"代码坏了，测试会报错"。思想叫**变异测试**：故意把代码改错一行（比如把 `>` 改成 `<`），测试**应该挂**；如果测试还绿着，说明测试是假把式，重写。

**对应本框架**：§6 Do 第3条「Verification-before-Completion」（每个 task 实际跑验证、看到预期结果才打勾）。

> 类比：烟雾报警器——你得先点根烟试试它响不响；要是着火了它还不响，这报警器等于没装。

### 闸门4：你拍板——人工签收（Human sign-off）

**做什么**：AI **不能自己说"做完了"**。要你明确确认——"我看了第 X 行 / 第 Y 条 AC，这条过了"。**"应该没问题""我检查过了"不算签收**，必须指出具体看了哪条。

**对应本框架**：§4 HARD-GATE 确认词范围（"可以/行/好"才算；"嗯/你看着办/再看看"不算）+ Red Flags #12「没验证就说做完了 = 偏离」。

> 类比：交房你得住进去试水试电、逐项打勾签字，不能听开发商说"肯定没问题"就收房。

## 验收三态：PASS/BLOCK/WAIVER【硬性】

> 4 道闸门是"过程把关"，三态是"结果判定"。闸门全过 ≠ PASS（还需产出实际跑通）；闸门有阻塞 ≠ FAIL（可能是外部依赖缺失的 BLOCK）。本节定义验收的最终判定三态，杜绝"假装通过"和"莫名失败"两种偏离——这是 §6 /check 第5条「对照 spec 逐项核对」的判定结果落地。

### 三态定义

| 状态 | 定义 | 判定证据 | 适用场景 |
|------|------|----------|----------|
| **PASS** | 验收项实际跑通，产出符合 spec 预期 | 文件路径 + 行号 + 实际跑通的输出截图或日志 | 文件存在 / 代码可执行 / 测试通过 |
| **BLOCK** | 验收项因外部依赖缺失 / 前置任务未完成 / 环境不可用而无法验证 | blocker 清单 + 解除条件 + 复跑计划 | 外部服务未部署 / 前置任务未交付 / 环境认证失败 |
| **WAIVER** | 验收项因业务原因跳过（场景已废弃 / 功能不再需要） | 用户明确批准 + 跳过理由 + 影响面分析 | 旧场景废弃 / 功能合并 / 优先级调整 |

### 三态硬规则

- **PASS 必须"跑通"才算数**：不能"我觉得应该没问题"，必须有实际执行输出作为证据（具体证据要求见下节「文件事实优先」）
- **BLOCK 不算失败，但不允许"假装通过"**：必须明确列出 ①blocker 清单（具体是什么阻塞）②解除条件（满足什么才能复跑）③复跑计划（blocker 解除后怎么继续）。BLOCK 不计入"已完成"，但也不计入"失败"——它是"待复跑"
- **WAIVER 永远是"明确批准 + 留痕"，不是"忘了跑"**：必须 ①用户明确批准（确认词范围见 SKILL.md §4 HARD-GATE 确认词）②记录跳过理由（为什么跳）③影响面分析（跳过会波及哪些功能 / 验收项 / 后续任务）。WAIVER 不允许 agent 自行决定，必须用户拍板

### 三态判定流程

```
验收项 → 跑验证
│
├─ 跑通且产出符合 spec 预期 → ✅ PASS（记录证据：文件路径+行号+输出）
│
├─ 跑不通，根因是外部依赖/前置/环境 → 🟡 BLOCK（列 blocker 清单+解除条件+复跑计划）
│
├─ 跑不通，根因是代码/逻辑问题 → 🔴 不算 BLOCK，回 /do 修补（不算验收态，是执行态）
│
└─ 业务上不再需要此验收项 → ⚪ WAIVER（用户明确批准+留理由+记影响面）
```

### 与 4 道闸门的关系

4 道闸门是**过程把关**（规格自检 / 差别核对 / 测试抓错 / 人工签收），三态是**结果判定**（最终落字 PASS / BLOCK / WAIVER）。两者关系：

- 闸门1（规格自检）不过 → 不许进 Do，不存在三态判定
- 闸门2-3 不过 → 回 /do 修补，不算 BLOCK（代码问题不是 blocker，是执行问题）
- 闸门4（人工签收） → 用户基于三态判定结果签收，签收时必须明确指出"X 项 PASS，Y 项 BLOCK + 复跑计划，Z 项 WAIVER + 影响面"

> 类比：4 道闸门是"装修时各阶段验收"，三态是"最终交房时的清单签字"——每项要么过（PASS）、要么卡住待修（BLOCK）、要么双方同意取消（WAIVER），不允许"应该没问题"或"假装没事"。

## 文件事实优先【硬性】

> 这是验收证据的硬规则：文档 / 口述 / 记忆 都不算证据，只有「文件内容 + 实际跑通日志」算证据。本节定义"什么算证据、什么不算证据、证据怎么记"，杜绝"我记得改过""之前跑过"的伪验收——这是 SKILL.md §0 RAM/Disk 心智模型在验收场景的具体落地。

### 证据判定标准

| 来源 | 是否算证据 | 说明 |
|------|------------|------|
| 文件内容（当前实际打开看到的） | ✅ 算 | 必须是当前文件状态，不是历史版本 |
| 实际跑通的输出日志 / 截图 | ✅ 算 | 命令 + 输出 + 时间戳三件套 |
| 文档里写的"已完成" | ❌ 不算 | 文档可以是过时的，必须以文件内容 + 实际跑通为准 |
| 口述"我之前跑过" | ❌ 不算 | RAM（上下文）是易失的，与 §0 RAM/Disk 心智模型一致 |
| 记忆里"我记得改过" | ❌ 不算 | 视为未验收，必须重新打开文件 + 重新跑验证 |
| 之前的对话截图 | ❌ 不算 | 只能证明"做过"，不能证明"现在还成立" |

### 硬规则

1. **任何"我记得改过""之前跑过"的表述视为未验收**：必须重新打开文件 + 重新跑验证，看到当次实际输出才能判定
2. **跑验证时必记四件套**：文件绝对路径 + 行号范围 + 执行命令 + 实际输出（可截断，但保留关键证据行，如 PASS/FAIL 行、错误码行、关键数值行）
3. **验收报告必须按固定格式逐条列出**：

```
验收项 X：{验收项名称}
- 文件路径：{绝对路径}
- 行号范围：{起始行-结束行}
- 验收命令：{实际执行的命令}
- 实际输出：{关键输出行，可截断}
- 判定：PASS / BLOCK / WAIVER
  - 若 BLOCK：blocker 清单={...}，解除条件={...}，复跑计划={...}
  - 若 WAIVER：用户批准={确认词}，跳过理由={...}，影响面={...}
```

### 与 §0 RAM/Disk 心智模型的关系

本节是 SKILL.md §0 RAM/Disk 心智模型在验收场景的具体落地——RAM（上下文 / 记忆）是易失的，不能作为证据；Disk（文件）是持久的，必须以文件实际状态为准。验收时"凭印象" = 违反 RAM/Disk 心智模型 = 偏离（触发 SKILL.md §7 Red Flags"凭印象回答"信号）。

> 类比：法庭只认物证（文件内容）+ 当庭演示（实际跑通），不认证人证词"我记得他做过"。验收也一样——文件说了不算，文档说了不算，只有当庭（当下）演示一遍才算数。

## 四、和本框架现有机制的关系（不重复造轮子）

本文件是"**定标准**"，另外两个文件是"**执行验收**"。三者配合 = 严格验收闭环，互不替代：

| 文件 | 角色 | 解决什么 | 阶段 |
|------|------|----------|------|
| **本文件 acceptance_criteria.md** | 定标准 | "验收标准长什么样、怎么写、几道闸" | Plan（写标准）+ Check（对照） |
| `references/common/pc/adversarial_review.md` | 找茬执行 | 独立视角挑逻辑漏洞 / 边界 case（6 维度） | Plan（写后审）+ Check |
| `references/check/red_flags.md` | 偏离报警 | AI 想偷懒跳过规则时，16 条信号立即停 | Check（全程） |

**闭环怎么走**：
```
写 spec 时定 AC（本文件第二节）→ 对抗性审查挑 AC 漏洞（adversarial_review.md）
        → Do 阶段逐条做 → 验收过 4 道闸门（本文件第三节）
        → 过程中任何"想跳过"被 Red Flags 拦下（red_flags.md）
        → 你逐项签收（闸门4）
```

## 五、多轮验收（一次次收紧）

不同类型任务，验收深度不同，但**闸门4（你签收）永远最后一道、不可省**：

| 任务级别 | 验收流程 | 关键动作 |
|----------|----------|----------|
| **简单**（一句话说清） | 对照 spec/AC 逐条打勾 → 你确认 | 过闸门2（差别核对）+ 闸门4（签收） |
| **复杂**（一句话说不清） | 对抗性审查 HIGH 清零 → DoD 检查 → 逐条 AC → 你签收 → Reflexion 反思 | 4 道闸门全过 + 对抗性审查 |
| **大改**（≥3文件 / ≥100行 / 核心模块） | 同复杂，且**强制**跑对抗性审查（§6 /plan 步骤6（对抗审查子项）） | 闸门3（测试抓错）必须做 |

> 详细阶段定义见 `SKILL.md §4 任务分级` 与 `§5 工作阶段`、§6 Check。

## 六、0 基础常见 4 个坑（必看）

| # | 坑（错误做法） | 为什么错 | 正确做法 |
|---|---------------|----------|----------|
| 1 | 只说"做好就行" | 没标准 = 没验收，AI 自己定标准一定偏 | 用第二节 Given/When/Then 写 AC |
| 2 | 验收标准写"性能好" | "好"没法测量，AI 怎么交都行 | 写"响应 < 500ms""错误率 < 1%" |
| 3 | AI 说"应该没问题"就放过 | 不算签收，可能根本没验证 | 要 AI 指出"看了第 X 行 / 第 Y 条 AC" |
| 4 | 没写"不做的事" | AI 容易画蛇添足，多改出 bug | 闸门1 第3块：明确列 Non-goals |

## 七、验收前自检清单（照着过一遍）

验收前，AI 和你要一起过这 4 条；**有任何一条不过，不算做完**：

- [ ] **DoD 通用底线过了吗？**（闸门1 的 5 块都写了、规矩合规）
- [ ] **每条 AC 是 Given/When/Then、能测量的吗？**（第二节三条硬性规则）
- [ ] **4 道闸门逐道过了吗？**（规格自检 → 差别核对 → 测试抓错 → 你签收）
- [ ] **你明确签收了吗？**（不是"应该没问题"，是指出具体看了哪条）

## 八、L1/L2 任务验收标准

### L1（Report-only）
- [ ] 输出符合 triage 三段式：High Priority / Watch / Noise
- [ ] 不修改业务代码、配置文件或脚本
- [ ] 所有结论有依据，引用来源或推理过程
