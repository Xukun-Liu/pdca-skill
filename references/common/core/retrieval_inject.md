# 检索注入规则（Retrieval Inject · C6）
> 阶段标签：P.route · D.comm · C.verify

> 版本：v1.1.0 | 更新：2026-10-28

## 📖 什么时候读这个文件

- 你要把检索结果（网页、文档、代码、记忆、清单）塞进上下文之前
- 你已经搜到很多条，但不确定该放多少、放哪几条
- 对话变长、开始「记住前半段忘了后半段」时（过载前兆）

## 一、第一性原理

上下文是**预算**，不是仓库。检索注入的唯一目标：**用最少的 token 让下一步决策不再靠猜**。

三条硬约束：

| 约束 | 含义 | 违反后果 |
|---|---|---|
| 相关性优先 | 只注入能改变「下一步动作」的条目 | 注入一堆正确但无用的内容，等于没注入 |
| 分层注入 | 先摘要，命中再加片段，确认要引用才取全文 | 一次注入全文，后面没预算干活 |
| 可回溯 | 每条注入内容带来源（路径 / URL / 记忆条目名） | 结论无法核对，等于编造 |

## 二、三档注入（默认从低档起）

| 档位 | 注入内容 | 单条预算 | 使用时机 |
|---|---|---|---|
| L1 摘要 | 标题 + 1 行结论 + 来源 | ≤ 40 字 | 初筛、判断「要不要展开」 |
| L2 片段 | 命中段落原文（±2 行上下文）+ 来源 | ≤ 200 字 | 需要依据、需要引原话 |
| L3 全文 | 整文件 / 整页 | 视预算 | 即将改这个文件、或要做逐条核对 |

**升级规则**：L1 判定相关 → 再取 L2；L2 里出现「要改的行 / 要引的原文」→ 才取 L3。
**降级规则**：L3 取回后发现只用得上一段，下一轮同类检索直接用 L2。

## 三、注入预算（按任务类型）

| 任务类型 | 检索注入总预算 | 单轮条数上限 |
|---|---|---|
| 问答 / 解释 | 上下文 20% | 5 条 |
| 改代码 / 改文档 | 上下文 30% | 8 条 |
| 调研 / 汇报 | 上下文 40% | 12 条（每条 L1 起） |
| 长任务（多批次） | 每轮重算，不累计 | 每轮 8 条 |

超预算时按「能不能改变下一步动作」砍，不按「看起来重不重要」砍。

## 四、排序与去重（注入前必做）

1. **去重**：同一来源只留一条（同 URL、同文件、同记忆条目名视为同一来源，保留信息量最大的那条）
2. **排序**：一手来源 > 二手转述；本项目文件 > 外部网页；官方文档 > 博客/论坛
3. **冲突**：两个来源矛盾时**两条都留**并标注冲突，不擅自选一个
4. **时效**：涉及版本号、价格、API 签名的内容必须带日期；过期来源标注「可能已过期」

## 五、注入格式（缺一项算不合格）

```
[来源] <路径 或 URL 或 memory_rj/... 条目名>
[时间] <YYYY-MM-DD，外部来源必填>
[档位] L1 / L2 / L3
[内容] <摘要 / 片段 / 全文>
```

对话里可以压缩成一行：`来源：<路径>（2026-10-28，L2）<片段>`，但四要素不能少。

## 六、与其它硬门的联动

| 联动对象 | 规则 |
|---|---|
| 口径三状态（阶段6） | 注入的数字必须带口径：`88.52｜官方口径｜来源` / `xx.xx｜来源待补` / `暂无数据` |
| 记忆（memory_rj） | 优先注入记忆条目（已压缩过），没有再回读原始文档 |
| 清单（inventory.py） | 需要「有哪些文件」时用清单，不要靠 Glob 猜路径 |
| 写后校验（C4） | 注入内容用于改文件后，照常做写后四查 |

## 七、反模式（命中即返工）

| 反模式 | 现象 | 正确做法 |
|---|---|---|
| 全文倾倒 | 一次贴 3 个文件全文 | 先 L1 摘要，按需升级 |
| 无源注入 | 「我记得大概是……」 | 带路径/URL，或直接说「暂无数据」 |
| 重复注入 | 同一份内容每轮都贴 | 首轮注入后只引用条目名，不重复贴 |
| 无限追加 | 上下文越滚越大 | 每轮重算预算，超出即压缩成条目名 |
| 沉默截断 | 检索结果被截断但不说明 | 明确写「结果被截断，共 N 条，取前 M 条」 |

## 八、验收（自查 4 问）

1. 每条注入都带来源了吗？
2. 有没有一条是「正确但不影响下一步动作」的？有就删
3. 有没有本可以 L1 却用了 L3 的？有就降档
4. 数字口径齐了吗（官方口径带来源 / 来源待补 / 暂无数据）？
