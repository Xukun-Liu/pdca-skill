# 系统化调试方法论
> 阶段标签：D · C（旧标签，以头部 PDCA 标签为准）

> 版本：v1.1.0 | 更新：2026-07-06

### 🐛 错误处理决策树

```
出错了/报错/结果不符合预期
│
├─ 第一步：立即承认失败 + 把错误翻译成大白话（不辩解、不归因）
│
├─ Attempt 1（第一次尝试修复）
│   ├─ 记录：我要做什么修复，基于什么分析
│   ├─ 执行修复
│   └─ 验证
│       ├─ fixed → 记录Error Log → Reflexion三问 → 写memory → 结束
│       └─ failed → 记录"试了什么、为什么没用" → Attempt 2
│
├─ Attempt 2（换方法，不重复1的思路）
│   ├─ 记录：换了什么新角度
│   ├─ 执行新修复
│   └─ 验证
│       ├─ fixed → 记录Error Log → Reflexion三问 → 写memory → 结束
│       └─ failed → 记录 → Attempt 3
│
├─ Attempt 3（重新审视根因）
│   ├─ 停下来重新想：我是不是理解错了问题本身？
│   ├─ 换一个完全不同的方向
│   └─ 验证
│       ├─ fixed → 记录Error Log → Reflexion三问 → 写memory → 结束
│       └─ failed → 立即ESCALATED升级给你
│           └─ 说明：已尝试X/Y/Z三种方法都不行，需要你的判断
│
└─ 修复后必做 → Reflexion三问【硬性】
    ├─ 我预期会怎样？实际发生了什么？（差距是什么）
    ├─ 为什么有差距？我没遵守规则？还是规则有缺口/不清晰？
    └─ 如果是规则缺口→具体场景是什么→记录到MEMORY.md经验栏
```

> 📖 **什么时候读这个文件**：
> - 遇到错误/报错/结果不符合预期
> - 准备尝试任何修复前
> - 想试第三次同一方法前（3-Strike升级点）
> - 修了一次没好
> 🔴 **不要在这时候读**：
> - 只是正常写代码/回答问题，没有出错
> - 已经在按明确task步骤执行且没报错

## 1. 遇到问题时的第一反应

不管是代码报错、命令失败、结果不符合预期、还是AI自己判断出错，严格按以下流程执行，不要凭直觉乱试。

---

## 2. 四步调试法

### Step 1：复现（Reproduce）

目标：稳定地重现问题，而不是"偶发"。

- 记录复现步骤：1、2、3……做了什么导致问题出现
- 明确预期 vs 实际：「我期望发生X，实际发生了Y」
- 收集完整错误信息：错误堆栈、终端输出、日志——复制原文，不要概括
- 确认问题可复现：再试一次，是必现还是偶现？

**反模式**：
- 只贴一行错误说"报错了"——没有复现步骤等于没说
- 改了一堆东西然后说"修好了"——不知道改了什么修好的=没修

### Step 2：隔离（Isolate）

目标：缩小问题范围，找到真正的出错点。

- **二分法定位**：注释掉一半代码/回退到上一个能工作的版本，看问题还在不在
- **一次只改一个变量**：不要同时改A、B、C，你不知道哪个起了作用
- **最小复现案例**：把问题简化到最小的可复现示例（比如从100行代码缩到10行）
- **区分根因和表象**：报错说"变量未定义"，根因可能是这个变量根本没被创建，而不是"加个变量定义就行"

**你0基础类比**：像修灯不亮——先看灯泡坏没坏（换一个试试），再看开关坏没坏，再看保险丝，再看整栋楼有没有电。不要一上来就 rewiring 整栋房子。

### Step 3：最小修复（Minimal Fix）

目标：修复根因，不做顺手重构。

- 找到根因后，做**最小范围**的修复
- **Surgical Changes（手术式修改）原则**：只改必须改的那几行，不顺手重命名、不顺手重构、不顺手优化其他地方
- 修复后立刻验证：复现步骤走一遍，问题解决了吗？
- **Chesterton's Fence**：如果为了修复需要改动一段"看起来很奇怪"的旧代码，先搞懂它为什么这么写，再动

**反模式**：
- "反正都打开了顺便重构一下"——会引入新bug
- 一次改10个文件然后祈祷能跑——大概率跑不起来，而且不知道哪里错了

### Step 4：验证（Verify）

目标：确认修复有效，且没有引入新问题。

- 走一遍复现步骤：原来的问题没了吗？
- 跑相关测试：如果有测试的话
- 检查周边功能：修复这个问题有没有破坏其他东西？
- 记录结果：把错误现象、尝试次数、解决方法写入错误记录表

## 3. 3-Strike Error Protocol（三振错误协议）

配合四步调试法使用，明确"试几次该放弃"的阈值。

### ATTEMPT 1（第1次）：诊断与精准修复

执行四步调试法 Step 1→2→3→4。
- 仔细读错误信息
- 做最小范围修复
- 记录到错误表（Attempt=1）

### ATTEMPT 2（第2次）：换方法

第一次修复后问题依旧，或者修复引发了新问题？
- **不要重复同样的操作！** 同样的方法做第二次只会得到同样的失败
- 换工具、换库、换思路、换实现方式
- 重新走四步调试法，可能你隔离的根本就不是根因
- 记录到错误表（Attempt=2，写明换了什么方法）

### ATTEMPT 3（第3次）：重新思考

第二次也失败了？停下来。
- 质疑你的基本假设：你对问题的理解可能从一开始就是错的
- 搜索解决方案：查文档、搜错误信息、看有没有人遇到过类似问题
- 重读需求：你是不是理解错了用户要什么？
- 考虑更新计划：可能是计划本身有问题，不是执行的问题
- 记录到错误表（Attempt=3，写明重新思考后的新方向）

### AFTER 3 FAILURES（3次都失败）：升级给你

3种方法都试了还不行？停止尝试，不要继续瞎试浪费token。
- 停止所有尝试
- 清楚说明：
  - 我要做什么
  - 我试了哪3种方法（详情见错误记录）
  - 每次具体报什么错
  - 我猜测可能的原因是什么
- 问你要方向：「你，这个问题我试了3种方法都没解决（错误记录在XX），您看是换个思路还是先跳过做别的？」

**硬规则**：3次失败必须升级，不允许试第4次。

## 3.5 Reflexion：修复后/升级前的结构化反思

解决一个错误后（无论是修复成功还是3次失败升级），必须做一轮结构化自我反思：

**反思三问**：
1. 我预期会怎样？实际发生了什么？（差距是什么）
2. 为什么会有这个差距？是我没遵守规则？还是规则有缺口/不清晰？
3. 如果是规则缺口，**具体场景**是什么？

- 如果结论是"我没遵守规则"→ 不记录，但自己记住下次遵守
- 如果结论是"规则有缺口/不清晰"→ 记录到MEMORY.md经验栏，附具体失败案例
- 如果是3次失败升级→ 反思结果附在给你的升级说明里

## 4. 错误记录规范

每次错误都必须记录，格式见 task_template.md 的错误记录表。

| 列 | 填什么 |
|----|--------|
| 时间 | HH:MM 格式 |
| 错误现象 | 粘贴原始错误信息，用大白话补充说明出了什么问题 |
| 第几次尝试 | 严格按3-Strike递增：1→2→3 |
| 怎么解决的 | Attempt 1/2/3 各用了什么方法、结果如何；3次失败写"已升级你" |

## 5. 常见 Debugging 反模式

| 反模式 | 为什么不对 | 正确做法 |
|--------|-----------|----------|
| 随机改代码碰运气 | 浪费时间，可能引入新bug | 用四步调试法，先复现再隔离 |
| 不看错误信息就谷歌/搜索 | 错误信息里往往已经告诉你答案了 | 先仔细读完错误信息再行动 |
| 一次改很多东西 | 不知道哪个改动起了作用 | 一次只改一个变量 |
| 忽略警告信息 | 警告往往是错误的前兆 | 警告也要看，搞清楚在警告什么 |
| "这不可能出错啊" | 代码不会撒谎，出错了一定有原因 | 放下预设，用二分法找证据 |
| 修复后不验证 | 可能修复了表象没修复根因 | 修复后必须走复现步骤验证 |
| 重复同样的失败操作 | 精神内耗，浪费token | Attempt 2就必须换方法 |
| 不记录错误 | 下次遇到同样问题还会踩坑 | 每个错误都记入Error Log |

## 6. 类比库（给你解释debugging用）

| 技术概念 | 大白话类比 |
|----------|-----------|
| 复现bug | 医生看病要先看到症状，不能听你说"我偶尔头疼"就开药 |
| 二分法定位 | 查字典——先查一半，看在不在前半本，再查一半的一半…… |
| 最小修复 | 手上扎了个刺——把刺挑出来就行，不要截肢 |
| 3次失败升级 | 问路问了3个人都不知道怎么走，就别再乱走了，找个靠谱的人问清楚或者换个目的地 |
| 不重复失败 | 门锁了，第一次用钥匙开没开，第二次换个钥匙，第三次找开锁的——不要反复拧同一把错钥匙 |
