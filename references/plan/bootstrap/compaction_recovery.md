# 上下文压缩恢复协议（Compaction Recovery Protocol）【硬性】
> 阶段标签：P（旧标签，以头部 PDCA 标签为准）

> 版本：v1.0.0 | 最近更新：2026-07-21 | PDCA 标签：P.bootstrap
> 对应 SKILL.md 章节：§1.5 上下文压缩恢复协议

> 规则在 SKILL.md 前端（不易被压缩），记忆在文件系统（必须主动读取）。
> 压缩后只重读规则 = 只恢复了"怎么做"，没恢复"在哪、做了什么、为什么"。
> 本文件从 SKILL.md §1.5 下沉而来，作为按需加载的详细流程。

## 检测信号

以下任一信号出现时，视为可能发生了上下文压缩，立即执行恢复流程：

| # | 信号 | 来源 |
|---|------|------|
| 1 | 对话超过 10 轮 | 主动压缩代理信号① |
| 2 | 单轮输出超过 200 行 | 主动压缩代理信号② |
| 3 | 累计读取文件超过 10 个 | 主动压缩代理信号③ |
| 4 | 感觉"我好像忘了什么" | 五问触发条件 |
| 5 | 连续 3 次回答未引用文件 | 规则衰减信号 |
| 6 | 发现自己在"凭印象"回答 | 规则衰减信号 |

## 恢复流程（7 步）【硬性】

检测到上述任一信号 → 按顺序执行，不可跳步：

1. **停下** — 不继续当前输出，暂停手中动作
2. **读 SUMMARY** — 读 `{主docs}/SUMMARY_RJ.md`，恢复"在哪"（全局文档索引）
3. **读 MEMORY** — 读 `memory/memory_main.md`（全局聚合）+ 项目 `docs_rj/memory_rj/{任务名}_memory_*.md`，恢复"做了什么"（按项目分段）
4. **重读铁律** — 重读 SKILL.md 7 条铁律，恢复"怎么做"（行为规则）
5. **过五问** — 执行 5-Question Reboot Test（见 working_memory_rules.md §4），确认上下文完整
6. **告知用户** — 一句话："检测到上下文压缩，已恢复记忆，继续 XX 任务"
7. **继续** — 恢复后继续之前的工作

> 文件缺失时降级：SUMMARY 或 memory/memory_main.md 不存在 → 走 SKILL.md §1 Bootstrap 初始化，不凭记忆编造。

## 压缩前关键清单外置【硬性】

**触发条件**：检测到压缩代理信号①②③（对话超10轮/单轮超200行/累计读取超10个文件）时，**在压缩前**先做一次"关键清单外置"，避免压缩后无法核对任务全貌。

**问题场景**：29 任务清单只在压缩后的对话总结里，T28 阻塞时无法核对 29 任务是否全做，只能靠 commit 摘要数出 18 个有编号任务。

**外置操作（3 步）**：

1. **写 task 清单到 memory**：经 `write_project(task, content)` 写入 `docs_rj/memory_rj/{task}_memory_*.md`，content 含：
   - **任务清单**：所有任务编号 + 状态（completed/in_progress/blocked/skipped）+ commit hash（若已 commit）
   - **当前进度**：已完成批次数 / 总批次数 + 当前批次在做哪几项
   - **阻塞项**：BLOCKED/SKIPPED 的任务及原因
2. **更新 TASK_STATE.md**：若 handoff_tidy 未自动更新，手动写一次 `docs_rj/memory_rj/TASK_STATE_{task_id}.md`，status 字段反映真实状态（completed/paused/blocked）
3. **commit 锁定**：git add + commit，确保压缩后能从 git log 看到完整任务清单

**与 §6 /plan 步骤6 补充的关系**：
- §6 步骤6 补充要求"大任务必落 spec/task 文件"——这是**事前预防**（任务开始前就写文件）
- 本节"压缩前关键清单外置"是**事中补救**（压缩发生时才写文件）
- 两者互补：事前已落 spec/task 文件的任务，压缩时无需重复外置；事前未落的（用户豁免的简单任务），压缩时必须外置

**降级**：若压缩信号未检测到（系统自动压缩未通知 agent），压缩后才意识到，则走本文件上方"恢复流程 7 步"，从 memory + TASK_STATE.md 恢复任务清单。
