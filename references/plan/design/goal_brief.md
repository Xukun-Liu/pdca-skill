# goal_brief：参考项目 机制详述（协作场景适配版）

> 阶段标签：P（旧标签，以头部 PDCA 标签为准）
> 版本：v1.0.0 | 更新：2026-07-30

> 参考项目 是 GitHub 上的任务下发器技能，5 步流程产出 ≤4000 字符任务书给外部 agent 独立跑。
> riji-skill 吸收其问题意识与解决方案，适配到"用户在场协作"场景——不派外部 agent，全在 riji-skill 里干。
> 本文件是 参考项目 机制的详述载体，SKILL.md 只放指针，模板只放字段骨架。

---

## 1. 六节结构（信息组织顺序映射到 spec 现有章节）

> 参考项目 原始六节：开头/我替领导拍的板/界限/现状与任务0/任务N/完成条件。
> riji-skill 适配：不新增六节结构，映射到 spec 现有章节。

| 参考项目 六节 | riji-skill spec 章节映射 | 适配说明 |
|------------|--------------------------|----------|
| 开头（五件事各一句） | 拆分映射（见下方说明） | 五件事拆分：意图/让步顺序→spec §1.0 业务背景；死规矩与参考分界→task 总览项目纪律；我替领导拍的板→spec §10 Clarifications（详见下行）；一句话目标→task 总览最终目标 |
| 我替领导拍的板 | spec §10 Clarifications | 没问出口的决定 → 澄清增量记录，每答即写回 |
| 界限（白名单/判卷冻结/顺手活） | spec §5 验收标准 + task 改动白名单 | 白名单→task 改动白名单路径字段；判卷冻结→spec §5 判卷冻结声明；顺手活→task 阻塞项字段 |
| 现状与任务0 | spec §1.X 富规格引用 + task T001 前提核验 | 实测数字→spec 富规格引用路径；任务0→/do 第一个 task 前跑命令核对基线 |
| 任务N | task.md 逐项 | 每个任务含目标带数字/死规矩带后果/验收=命令+判定/反向验证 |
| 完成条件 | spec §5 完成条件双指标 | 两条硬指标：结果指标+约束指标 |

**核心差异**：参考项目 的"中途没人可问"在协作场景不成立（用户在场），所以"我替领导拍的板"改为"澄清增量记录"（用户可随时回答），"BLOCKED.md"改为 task 总览"阻塞项"字段（随交付提交空也写"无"）。

## 2. 4000 字符硬上限 → 信息密度指引（单节≤500字）

> 参考项目 的 4000 字符硬上限是 `/goal` 命令的物理限制——超了粘不进去。
> riji-skill spec 落文件无此限制，但信息密度问题依然存在——spec 太长 = agent 读不完 = 等于没写。

**适配方案**：4000 字符硬上限转为"信息密度指引"：
- 单节 ≤500 字，超了评估拆分
- 超 500 字的节须在节首注明"本节因 XX 原因超 500 字"
- 字符花在"不查就会踩的坑"上，不写"打开仓库一眼能看到的事实"
- 砍调研过程、重复规矩、背景故事

**与 spec_template.md 的关系**：spec_template.md 文档开头写作指引已含"信息密度指引"项（REQ-031）。

## 3. 防五种死法（协作场景适配）

> 参考项目 防执行 agent 的五种死法，协作场景下 agent 仍可能犯，全保留。

### 3.1 作弊达标（最重要）

**问题**：说"让测试绿"，最省力的是加 `.skip`、放松断言、mock 被测对象、删测试、`|| true`——不是它坏，是目标函数写错。

**对策（协作场景适配）**：
- **基线不可退**：测试数/覆盖率 ≥ 基线、skipped 0（spec §5 基线数字列）
- **点名禁止具体姿势**：skip/todo/mock/删测试/改阈值/||true 全算失败（task 防作弊点名禁止字段）
- **判卷标准冻结**：测试/验收脚本/CI 配置不许碰（spec §5 判卷冻结声明）
- **暗卷自留**：2-3 条 spec 没写的抽查项（task 验收清单闸门5）
- **characterization test**：若"测试要绿"与"实现不许改"冲突而代码真有 bug——锁当前行为+标 KNOWN DEFECT，否则 agent 必偷改实现（spec §9.1）

### 3.2 幻觉命令

**问题**：agent 会平静地编造命令再甩锅环境。

**对策**：
- spec 里每条命令 agent 必须亲手跑过（task 防幻觉验证字段）
- 摸不到的写进 task 让用户实测
- /plan 步骤4 加"实测命令真实性"+"假绿灯检查"（lint 是 echo 占位/没 import 的文件从覆盖率消失/README 命令不存在）

### 3.3 失忆

**问题**：跨对话/上下文压缩后 agent 忘了做到哪。

**对策（协作场景适配）**：
- 进度写 task 总览"进度状态"字段（对应 PROGRESS.md）
- 阻塞写 task 总览"阻塞项"字段（对应 BLOCKED.md）
- 开工回执 ≤10 行：理解的目标/顺序/最大风险，协作场景下呈现给用户核对（task 总览开工回执字段）
- riji-skill Memory First 硬规则 + write_project 自动落盘，跨对话恢复更强

### 3.4 一条道走到黑

**问题**：agent 撞墙不回头，烧预算。

**对策**：
- 任务0 前提核验：第一个 task 前跑命令核对基线数字，对不上就停（/do 章节任务0机制）
- 连败3次换项：同一验收连败3次换下一项（与3-Strike独立计数：3-Strike是错误处理，连败3次是验收失败）
- 失败回滚：结果比基线差就回滚如实报告——"没做成但说清了"合格，"做了但更糟"不合格
- 止损满轮即停：跑满 N=3 轮即停，如实汇报卡在哪（N=3 与对抗审查3轮上限对齐）

### 3.5 静默事故

**问题**：坏了不发信号的（假绿灯、失效报警器）。

**对策**：
- 反向验证：凡是"坏了没人会知道"的检查都要——故意制造一次失败证明会响，贴红→还原贴绿
- task 反向验证字段：仅"失效不报警会出事故"的验收项强制为"是"
- 验收清单闸门6：贴实际命令输出（含反向验证红→绿证据），只说做完了不算

## 4. 法与情报分家

> 参考项目 原始：「不许」是法，违反即不合格；「建议」是情报，执行者有更好的路可以走。
> riji-skill 已有【硬性】/【弹性】区分，本节强化对齐。

| 参考项目 概念 | riji-skill 概念 | 一致性 | 说明 |
|------------|----------------|--------|------|
| 法（不许，违反即不合格） | 【硬性】 | ✅ 一致 | 违反【硬性】=偏离，触发 Red Flags |
| 情报（建议，有更好的路可走） | 【弹性】 | ✅ 一致 | 【弹性】可按场景调整，记录理由 |
| 把情报写成法 = 替执行者做临场决定 | 禁止过度硬性化 | ✅ 一致 | riji-skill 已有"避免过度工程"原则 |

**写作指引**：
- spec 里每条规则标注【硬性】或【弹性】
- 【硬性】规则每条溯源到一次实测或一次用户裁决
- 【弹性】规则执行者有更好的路可以走，在 task 记录为什么走了别的路

## 5. 多 agent 地界机制（部分放弃）

> 参考项目 原始：多 agent 并行时，每份书带同一段"全局"，地界错开，共享写入点指定唯一归属。
> riji-skill §0.56 副 agent 只读调研，不并行执行——部分子机制不适用。

| 参考项目 子机制 | riji-skill 归属 | 理由 |
|--------------|----------------|------|
| 全局段（整体干什么/谁管哪段/接缝在哪） | 适配吸收 | REQ-019 适配为"副 agent 调研时传递全局上下文（整体干什么/调研哪块/结论回哪里）"，不是"谁管哪段/接缝"（副 agent 只读不"管"段） |
| 共享写入点归属（lockfile 指定唯一归属） | 显式放弃 | 副 agent 只读不写，无共享写入点冲突。§0.56 明确"副 agent 只读调研，所有写操作由主 agent 守 HARD-GATE 后执行" |
| A 证据过 B 战场只列存疑不动 | 显式放弃 | 副 agent 只读调研无"战场"，不适用 |
| 建设与删除不给同一 agent | 显式放弃 | 副 agent 只读不建设不删除，不适用 |
| 合并排队提示（不要自行协调、不要改 CI） | 显式放弃 | 副 agent 不合并不 CI，不适用 |

**结论**：5 个子机制中，1 个适配吸收，4 个显式放弃。放弃理由都是"副 agent 只读不写不并行执行"。

## 6. 明卷+暗卷验收

> 参考项目 原始：明卷（验收命令）在书里，执行者可见；暗卷（2-3 条抽查）自留在会话侧，执行者看不见。
> riji-skill 适配：明卷=spec §5 公开验收命令；暗卷=task 验收清单闸门5。

| 卷类型 | 参考项目 原始 | riji-skill 适配 | 落地位置 |
|--------|------------|----------------|----------|
| 明卷 | 任务书里的验收命令 | spec §5 验收标准表格（公开） | spec_template.md §5 |
| 暗卷 | 会话侧 scratchpad 自留 | task 验收清单闸门5（2-3 条 spec 没写的抽查项） | task_template.md 验收清单 |

**协作场景差异**：参考项目 的暗卷是"执行者看不见"（独立 agent），riji-skill 的暗卷是"spec 没写但 task 有"（同一 agent 可见，但 spec 没公开声明）。协作场景下暗卷的"突然性"弱于 参考项目，但仍能覆盖 spec 遗漏。

## 7. 探索型改四处

> 参考项目 原始：领导要答案本身（调研、选型、该不该做 X）时，硬指标只会换来凑数的答案，改四处。
> riji-skill 适配：spec §1.X 目标类型字段标注"执行型/探索型"，探索型改四处。

| # | 参考项目 原始 | riji-skill 适配 | 落地位置 |
|---|------------|----------------|----------|
| 1 | 完成条件换成学习目标 | spec §5 完成条件双指标改为"学习目标"：结论条数设上限、每条附来源与日期或可复跑的复现步骤——宁收 2 条实的，不收 10 条凑的 | spec_template.md §5 |
| 2 | 预算换成可承受损失 | spec §9 风险加"可承受损失"：最多烧多少时间/查多少来源，烧完就交卷，交"目前最优+还没排除什么" | spec_template.md §9 |
| 3 | 防作弊主防编造 | task 防作弊点名禁止加"凑数结论/查无此文的引用/没跑过的实测"都算作弊；每条结论要经得起随机抽一条、10 分钟内复现 | task_template.md 防作弊字段 |
| 4 | 此路不通=合格交付 | spec §5 完成条件加"带证据证明某方向是死路（死因+原始输出）按完成计" | spec_template.md §5 |

**与执行型的区别**：执行型全套照走标准验收流程（基线数字/判卷冻结/反向验证）；探索型验收降级为抽查点+用户亲验（spec §6 文风体验类任务验收降级）。
