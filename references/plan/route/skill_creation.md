# 建 Skill 参考（Skill 创建与迭代）

> 版本：v1.1.0 | 更新：2026-08-20
> 阶段标签：P.route

> 📖 **什么时候读这个文件**：
> - 用户要新建一个 skill（"帮我做一个 XX skill""把这套流程做成 skill"）
> - 用户要修改/优化已有 skill（"这个 skill 不好用，改改"）
> - 需要给 skill 设计测试用例 / 评估效果 / 优化触发描述时

🔴 **不要在这时候读**：

- 找现成 skill / 安装 skill → 走 [skill_management.md](skill_management.md)
- 只是调用已装好的 skill → 直接用，不读本文件

> ⚠️ **能力边界声明**：本文件覆盖**定性人审迭代循环**（出题→对比→人审→改进）。量化 benchmark 工具链（自动判分/方差统计/结果查看器/自动描述优化引擎）**不内置于本框架**——正文按"手工可落地"的等价流程写；如需完整工具链，见包级 `NOTICE` 所示外部开源资产（Apache 2.0）。

## 一、前置判断：找现成 vs 自己建

动手写之前先过这道闸（复用优先）：

| 问题 | 走向 |
|------|------|
| 已有现成 skill 能覆盖需求？ | 先走 [skill_management.md](skill_management.md) 搜索安装 |
| 找不到 / 不合适 / 要深度定制？ | 走本文件新建流程 |
| 当前对话里刚跑通一套流程，用户说"做成 skill"？ | 直接进 §二，从对话历史提取 |

## 二、开工前检查（改已有 skill 必做）

| 检查项 | 做法 | 原因 |
|--------|------|------|
| **快照旧版**【硬性】 | 改已有 skill 前，先整目录复制一份到 `{skill-name}.bak/` 或 zip；对比测试的 baseline 指向快照 | 一上手就编辑 = 旧版即丢，"旧版 vs 新版"的 baseline 无从谈起 |
| **保留原名**【硬性】 | 改进版仍用原 skill 名，**禁止输出成 `{skill}-v2`**（触发系统认名字，改名 = 换了个 skill） | 防止"改进"变成"新建" |
| **只读路径先拷出** | 目标 skill 若在只读/受管路径，先复制到可写工作区再改 | 直接改只读目录会静默失败 |
| **写入个人目录先确认** | 新建/改动落在 `~/.trae-cn/skills/` 等个人目录，动手前按 §10 安全边界向用户确认 | 个人目录属"碰之前先问"范围 |
| **非 git 目录备份** | 目标目录不是 git 仓库时，靠上面的快照步骤兜底回滚 | 铁律6 回溯保障的文件备份降级 |

## 三、意图捕获 4 问（写之前必答）

1. **这个 skill 要让 AI 能做什么**？（一句话能力描述）
2. **什么时候触发**？（用户会说什么话 / 什么场景下需要）
3. **期望输出格式**？（文件 / 代码 / 报告 / 结构化数据）
4. **要不要测试用例**？
   - 客观可验证产出（文件转换 / 数据提取 / 代码生成 / 固定流程步骤）→ 建议建
   - 主观产出（写作风格 / 艺术创作）→ 通常不需要，给建议但让用户定

**从对话历史提取**：若当前对话已包含用户想捕获的工作流，先提取——用了什么工具、步骤顺序、用户纠正过什么、输入输出格式。缺口问用户补齐，用户确认后再写。

## 四、访谈调研

主动追问边界 case、输入输出格式、示例文件、成功标准、依赖。写测试 prompt 之前先把这部分问透。

调研可并行（子agent 搜文档 / 找同类 skill / 查最佳实践），带着上下文来，减少用户来回回答的负担。

## 五、Skill 标准结构（四件套）

**落地目录（TRAE 环境）**：`~/.trae-cn/skills/{skill-name}/`（其他 Agent 的安装路径见 [skill_management.md](skill_management.md) 安装路径表）。**命名加 `_huihui` 后缀防与官方/第三方 skill 重名**（如 `pdf_tools_huihui`）。

```
skill-name/
├── SKILL.md        ← 必需：YAML frontmatter + Markdown 指令
└── 可选资源
    ├── scripts/    ← 可执行代码（确定性/重复性任务）
    ├── references/ ← 按需加载的文档
    └── assets/     ← 产出用的素材（模板/图标/字体）
```

| 目录 | 放什么 | 加载方式 |
|------|--------|----------|
| SKILL.md | name + description（frontmatter）+ 正文指令 | 触发即加载 |
| scripts/ | 确定性脚本（生成/转换/校验） | 直接执行，不占上下文 |
| references/ | 领域知识 / 变体文档 | 按需读 |
| assets/ | 模板等静态素材 | 产出时引用 |

**多领域变体组织**：skill 支持多框架/多平台时，按变体拆 references（如 aws.md / gcp.md / azure.md），SKILL.md 只留工作流 + 选择逻辑，AI 只读命中的那个变体文件。

## 六、三级渐进加载（token 优化的核心机制）

| 层级 | 内容 | 加载时机 | 预算 |
|------|------|----------|------|
| 1 元数据 | name + description | 永远在上下文 | ~100 词 |
| 2 SKILL.md 正文 | 工作流指令 | 触发即加载 | <500 行 |
| 3 捆绑资源 | scripts / references / assets | 按需 | 不限（脚本执行不占上下文） |

硬规则：
- SKILL.md 逼近 500 行 → 拆一层，加明确的"下一步去读哪个文件"指引
- 引用文件要在 SKILL.md 里写清**什么时机读**
- 大参考文件（>300 行）自带目录

## 七、SKILL.md 写法规范

### frontmatter（description 是主触发机制）

- description 写两样：**做什么** + **什么场景用**——所有"什么时候用"的信息放 description，不放正文
- **pushy 原则**：模型倾向"欠触发"（该用时没用），description 要写得主动一点。例：不只写"建 dashboard 的方法"，写"用户提到 dashboard / 数据可视化 / 内部指标 / 展示数据时都要用本 skill，即使没明说 dashboard"

### 正文写法

- **命令式**：直接下指令（"检查 X""输出 Y"），不绕弯
- **解释为什么**：讲清规则背后的原因 > 堆 MUST/ALWAYS——满篇大写强调是黄旗信号，模型够聪明，理解了 why 才能举一反三
- **示例模式**：

```markdown
**Example 1:**
Input: <输入长这样>
Output: <输出长这样>
```

- **输出格式模板**：要求固定结构时直接给模板：

```markdown
## 报告结构
ALWAYS 使用以下模板：
# [标题]
## 摘要
## 关键发现
## 建议
```

- **无意外原则**：skill 内容与其描述一致，不含恶意代码 / 越权行为 / 描述之外的隐藏动作

### 反模式（写完自查）

- ❌ 过拟合：只为手头几个例子生效（skill 是要泛化到上千次使用的）
- ❌ 堆砌僵硬的 ALWAYS/NEVER 而不解释原因
- ❌ SKILL.md 超长不拆层

## 八、测试迭代循环（定性人审版）

### 1. 设计测试用例

写完草稿，出 2-3 个**真实用户会说的话**（不是抽象指令——要带具体细节：文件名 / 列名 / 口语化表达），先给用户过目再跑。

⚠️ 别拿"读一下 X 文件"这种一步任务当用例——模型只对"自己搞不定的复杂多步任务"咨询 skill，一步任务不触发。

### 2. evals.json 格式（对齐框架自带体系）

evals 放 `{skill-name}/evals/evals.json`（跟 skill 走，不混入框架根 evals/）。条目格式与框架 `evals/evals.json` 一致（validate_skill.py INT-03 同构校验）：

```json
{
  "version": "1.0",
  "description": "XX skill 触发与产出评估",
  "evals": [
    {
      "id": "eval_trigger_dashboard_request",
      "name": "用户没点名skill但明显需要",
      "category": "trigger",
      "input": "帮我把这份数据做成内部指标页面，老板周五要看",
      "expected": "命中本 skill 并按其工作流执行",
      "assertion": "响应中体现 skill 工作流步骤",
      "source": "skill_creation.md §八"
    }
  ]
}
```

### 3. 对比运行（with vs baseline）

- **同轮发射**【硬性】：每个 case 的 with-skill 组与 baseline 组**同一轮全部发出**（用 Task 工具各起一个 fresh subagent，一个注入 SKILL.md、一个不带），禁止先跑完带 skill 组再回头补 baseline——时间差和上下文漂移会污染对比
- **运行期并行**：跑的同时起草断言，别干等
- **timing 即时落盘**：subagent 回报里的 `total_tokens` / `duration_ms` **当场**记入 `timing.json`——这是唯一捕获时机，错过后无处补采（token/时长是评估的一半价值）
- **workspace 组织**：结果按 `{skill-name}-workspace/iteration-N/{case名}/` 组织，**边跑边建目录不预建**；case 用描述性命名（禁 `eval-0` 这种）；每个新增/修改的 eval 记一条 `eval_metadata.json`
- **grading 契约**：人工判定结果写 `grading.json`，字段名固定 `text` / `passed` / `evidence`（将来接查看器/脚本校验强依赖这三个字段名，写错=静默断链）；可编程校验的断言优先写成脚本而非人眼判

### 4. 人类先看，AI 后改【硬性】

对比结果**第一时间呈现给用户**，先于人审完成之前不做自我修订——产出尽快怼到人眼前，这是迭代循环的灵魂秩序。用户反馈回来再改。

### 5. 反馈驱动改进（4 原则）

| 原则 | 做法 |
|------|------|
| 泛化反馈 | 别只修当前例子——过拟合修补没用；顽固问题换隐喻 / 换工作模式更划算 |
| 保持精简 | 不起作用的内容删掉；读执行记录（不只看产出），模型浪费时间的环节砍掉 |
| 解释为什么 | 把用户反馈背后的真实意图传进指令，而不是照抄抱怨 |
| 重复工作下沉 | 多个 case 都独立写了同款辅助脚本 → 写一次放 scripts/，以后直接用 |

### 6. 迭代终止与规模化

- 终止：用户满意 / 反馈全空 / 无实质进展 → 停
- **规模化**：小样本满意后，**扩大测试集、更大规模再试一轮**——小样本收敛≠skill 成熟

## 九、描述优化（进阶可选，放最后做）

⚠️ 时序：先把 skill 本体完全做完（§二-§八 收尾），再碰描述优化——提前调描述会白做。

触发评估集：约 20 条查询（10 条**应触发** + 10 条**不应触发**）。

- 应触发：同意图的不同说法（正式 / 口语 / 没点名 skill 但明显需要 / 罕见用法 / 与其他 skill 竞争但本 skill 该赢）
- 不应触发：**近似但不该命中的**——共享关键词但实际要别的（明显的无关反例没有测试价值）
- 查询要真实具体（文件路径 / 列名 / 公司名 / 口语 / 错别字混着来），不要抽象指令

**最小闭环四步**（无自动优化引擎时的手工等价流程）：

1. **出题**：按上述口径备 20 条查询
2. **人审**：逐条标注应触发/不应触发，剔除无效题
3. **跑优化循环**（手工版）：把查询按约 60/40 分训练/测试两组；对每条训练查询问"当前 description 会让模型触发吗"，统计触发率；迭代改写 description（每轮 5 次上限），**每组各跑 3 次取触发率**（单次判定噪声大）
4. **应用 best_description**：按**测试组**得分（不是训练组）选最优——按训练分选=过拟合；胜出后写回 frontmatter，向用户展示前后触发率对比

## 十、与 pdca-skill 的衔接（建完之后）

1. **登记（按产物类型分支）**：
   - **分支A 给 pdca-skill 新增 reference 模块** → 登记 SKILL.md 参考模块索引表（P 行）+ §3 资源索引 + references/index.md 速查表/反向索引 + trigger_hooks.md 触发行（四件套同步）
   - **分支B 建独立 skill** → **不动 pdca-skill 自身索引**（那是框架 reference 的索引，不是外部 skill 目录）；改为经 `write_project` 写 memory（skill 名 + 触发场景 + 安装路径），必要时在 skill_management.md 安装路径表核对目录约定
   - 🔴 禁止把独立 skill 登进 SKILL.md 索引表（语义错位：那里只登记框架自身 reference 模块）
2. **记忆**：经 `write_project` 记"建了 XX skill，触发场景 XX，路径 XX"
3. **触发实测**：交付前**开新对话**，用 §九 的应触发查询实测一次触发命中（触发系统按新对话加载 skill；当前对话验证不可靠）
4. **测试**：按 §八 至少跑一轮 eval 再交付，不裸交付
