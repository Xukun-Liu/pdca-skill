## Phase 1: 需求对齐

⚠️ **每个task必须包含以下字段**：
1. **做什么**（具体动作）
2. **怎么做**（完整代码/具体命令，无伪代码/无省略）
3. **怎么验证做完了**（具体验证步骤+预期结果）
4. **边界条件**（正常路径 + 边界/异常路径）
5. **验收标准（GWT）**（Given/When/Then，可测量）
6. **不通过处理**（验证失败时怎么回退/修复）
7. **实际跑了验证，看到预期结果，才能标记 [x]**

> leader 融合 v1.1.0 新增字段（REQ-033~037 + REQ-034a）：
8. **改动白名单路径**（REQ-033）：只允许改哪些文件，写明绝对路径
9. **反向验证**（REQ-034）：是/否——仅"失效不报警会出事故"的验收项强制为"是"
10. **防作弊点名禁止**（REQ-034a）：skip/todo/mock/删测试/改阈值/||true 全算失败（leader 防作弊第一死法的具体姿势）
11. **死规矩带后果**（REQ-035）：写成"做 A，否则 B"并带具体后果
12. **依赖排序说明**（REQ-036）：多任务按依赖排序，说清为什么它排前面
13. **防幻觉验证**（REQ-037）：命令必须亲手跑过，摸不到写进 task 让用户实测

> **字段豁免说明**（M2/M3 修复）：核对/审查/验收类 task（如对照清单核对、版本号同步检查、对抗审查）的"防作弊点名禁止"和"防幻觉验证"可标"N/A（核对/审查类任务，无代码改动/无命令执行）"；Phase 1 需求对齐类 task 可标"N/A（规划阶段，无执行）"。其他字段（改动白名单/反向验证/死规矩/依赖排序）必填。

## Phase 3: 验收

- [ ] T005 对照spec逐项验收
  - 怎么做：逐条核对spec文件的验收标准
  - 验证：所有验收标准项标记✓
  - 边界条件：
    - 正常路径：spec 验收标准清晰可测
    - 边界/异常：某条 AC 模糊 → 回 /plan 澄清后再验收
  - 验收标准（GWT）：
    - Given 打开 spec 和本 task
    - When 逐条核对 AC
    - Then 所有 AC 都通过，或明确记录未通过项及回退方案
  - 不通过处理：若有 AC 未通过，回 /do 修补或回 /plan 重设计

## 验收清单（4 道闸门 + leader 增强 3 项）

进入 Phase 3 前，逐条核对。有任何一条不过，不算做完。

- [ ] **闸门1 规格自检**：每个 task 都包含 5 个字段+新增字段？边界条件没空？验收标准写成 GWT？
- [ ] **闸门2 差别核对**：只改了声明要改的文件？没偷偷改别的文件？没私自加依赖？
- [ ] **闸门3 测试抓错**：每个验证命令实际跑过？故意把代码改错一行测试会挂？
- [ ] **闸门4 人工签收**：你明确说"可以/通过"，并指出具体看了哪条 AC/哪行代码？
- [ ] **闸门5 暗卷抽查**（REQ-042，leader 融合 v1.1.0）：2-3 条 spec 没写的抽查项，管理者自留，验收时复跑
- [ ] **闸门6 贴命令输出**（REQ-043，leader 融合 v1.1.0）：每条验收都贴实际命令输出（含反向验证红→绿证据），只说做完了不算
- [ ] **闸门7 止损满轮即停**（REQ-044，leader 融合 v1.1.0）：跑满 N=3 轮对抗审查即停，如实汇报卡在哪、还差什么

## 任务格式说明

**格式**: `- [ ] [TaskID] [P?] [Story?] Description with file path`

| 组件 | 必填？ | 说明 |
|------|--------|------|
| `- [ ]` | 是 | 复选框，标记完成状态 |
| `T001` | 是 | 任务ID，顺序递增 |
| `[P]` | 否 | 可并行执行时添加 |
| `[US1]` | 是 | 用户故事标签（Phase 1/2/3 除外） |
| Description + 文件路径 | 是 | 描述必须带具体文件路径 |
